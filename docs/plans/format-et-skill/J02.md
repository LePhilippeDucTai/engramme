# J02 — Boîte de réception et validation d'une base

Context: J01 est livré : `parse_note`/`read_note`, briques `pub(crate)` `source::lines`, `fence`, `frontmatter::{split, parse_fields, Field, note_frontmatter}`, `block::scan`, et `Diagnostic`/`DiagnosticKind`/`Parsed<T>` ; J02 ajoute l'API publique `parse_proposal(path: &Path, source: &str) -> Parsed<InboxProposal>` (pure), `read_proposal(path: &Path) -> Parsed<InboxProposal>`, `duplicate_ids(notes: &[Note]) -> Vec<Diagnostic>` (pure), `read_vault(root: &Path) -> Parsed<Vault>` (base entière, diagnostics triés par fichier puis par ligne) et `check_path(path: &Path) -> Vec<Diagnostic>`, point d'entrée de J03 (dossier → `read_vault`, fichier → note ou proposition selon son rôle, chemin illisible → `unreadable-file`) ; J03 résout `ENGRAMME_DIR`, affiche le `Display` de chaque diagnostic et calcule le code de sortie ; J04 et l'app réutiliseront tels quels les modèles `Serialize`.
Conventions (celles de J01, plus) : messages en anglais, sur une ligne, sans majuscule initiale ni point final, exacts entre « » (guillemets exclus) ; toute valeur citée dans un message (`target`, nom de fichier) a ses `\r` et `\n` remplacés par des espaces ; diagnostics d'un fichier triés de façon stable par ligne, ceux d'une base de façon stable par `(file, line)` selon l'ordre de `Path` (`sort_by(|a, b| a.file.cmp(&b.file).then(a.line.cmp(&b.line)))`) ; variantes ajoutées à `DiagnosticKind`, code kebab-case identique au nom serde : erreurs `MissingRequiredKey` (`missing-required-key`), `InvalidTarget` (`invalid-target`), `NoCard` (`no-card`), `TooManyCards` (`too-many-cards`), `IdInProposal` (`id-in-proposal`), `DuplicateId` (`duplicate-id`), avertissements `UnexpectedFileName` (`unexpected-file-name`) et `NotAVault` (`not-a-vault`) ; ni regex ni nouvelle dépendance (analyse sur `as_bytes()`, une `&str` n'est découpée qu'après des octets ASCII vérifiés, pour ne jamais paniquer) ; ni `unwrap()`/`expect()` qui dépende d'un fichier, ni `#[allow(dead_code)]` ; `///` en anglais sur tout élément public (`#![deny(missing_docs)]`).
Décisions, proposition (§3.4) : frontmatter absent → une seule erreur ; frontmatter non fermé ou YAML invalide → la seule `invalid-frontmatter` de J01, sans contrôle des clés ; clé obligatoire absente → `missing-required-key` ligne 1 ; `null` ou chaîne blanche → `missing-required-key` sur la ligne du champ ; valeur d'un autre type → `invalid-frontmatter` ; `date` et `target` validées par les grammaires de T1, sans vérifier que la note cible existe (« nouvelle note à créer » est permis) ni ramener `\` à `/` (une seule forme, portable) ; `tags` et `sources` comme pour une note ; toute autre clé, `title` compris, va dans `extra` ; la règle « 1 à 3 » compte les lignes d'ouverture de type exactement `qa` ou `cloze`, bloc fermé ou non, avec ou sans erreur (ni `free`, ni `estimate`, ni type inconnu), pour qu'un bloc fautif ne déclenche pas en plus `no-card` et qu'un 4e bloc fautif soit de trop ; tout `{#…}` d'une ligne d'ouverture, même mal formé ou sur un type réservé, est un `id-in-proposal` (sinon un agent qui « corrige » un identifiant mal formé tombe sur l'erreur suivante), et une carte à identifiant est retirée de `cards` (convention J01 : pas de carte pour un bloc en erreur) ; nom de fichier hors convention → simple avertissement (le contenu suffit au tri).
Décisions, base (§3.1) : seuls `notes/` (récursif) et `inbox/` (à plat, sous-dossiers ignorés) sont lus — ni `.app/` (le journal n'est pas validé dans ce sous-projet), ni `.gitignore`, ni les autres fichiers de la racine ; seuls les fichiers d'extension exactement `md` comptent ; toute entrée rencontrée pendant le parcours dont le nom commence par `.` est ignorée, à toute profondeur (la racine, `notes/` et `inbox/` eux-mêmes ne sont pas concernés : une base `~/.savoir` fonctionne) ; entrées triées par nom à chaque niveau, ordre qui coïncide avec celui de `Path` ; un lien symbolique n'est suivi que s'il désigne un fichier ordinaire (liens vers un dossier, donc cycles, et liens cassés ignorés) ; `notes/` ou `inbox/` absent → vide, sans diagnostic ; les deux absents → avertissement `not-a-vault` sur la racine (piège `engramme check notes/`, sans faire échouer une base neuve) ; dossier illisible → `unreadable-file` ; doublons : seules les cartes produites des notes comptent (une carte d'inbox à identifiant est déjà un `id-in-proposal`), dans un même fichier comme entre fichiers ; chaque occurrence après la première (ordre de parcours, puis des lignes) reçoit l'erreur, qui cite la première ; un fichier isolé est une proposition si son dossier parent s'appelle exactement `inbox`, une note sinon, et ne voit que ses propres doublons (dans une base, c'est l'emplacement qui décide).
Tests : `crates/engramme-format/tests/inbox.rs` et `tests/vault.rs` (API publique seulement, un test nommé par règle, aides recopiées de `notes.rs` plutôt que partagées) ; fixtures `tests/fixtures/inbox/{valid,invalid}/<nom>.md` avec `<nom>.json`, bases `tests/fixtures/vault/{valid,invalid}/` avec `tests/fixtures/vault/{valid,invalid}.json` ; instantanés sans message ni chemin absolu (chemins relatifs à la racine, joints par `/`), régénérés par `UPDATE_FIXTURES=1` puis relus un à un ; dossiers temporaires au nom unique sous `std::env::temp_dir()` (motif de `temp_file`), supprimés en fin de test ; aucun nom de fixture ne diffère d'un autre par la seule casse (APFS) ; chaque check enchaîne fmt, clippy `-D warnings` et les tests concernés.
