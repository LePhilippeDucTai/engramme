# J03 — CLI `engramme check` et base d'exemple

Context: J02 fournit `engramme_format::check_path(&Path) -> Vec<Diagnostic>` (dossier → `read_vault`, fichier → proposition si son dossier parent s'appelle exactement `inbox`, note sinon, chemin illisible → `unreadable-file` ligne 1) et le `Display` de `Diagnostic` (`{file}:{line}: {severity}: {message} [{code}]`) ; T1 lui fait aussi compter les fichiers vérifiés, pour la ligne de bilan. Nouveau crate `crates/engramme-cli` : bibliothèque `engramme_cli` (`run`, `run_with`) et binaire de développement `engramme-dev` (`src/main.rs`, une ligne), nommé ainsi pour ne jamais masquer le lanceur `engramme` de la wheel (J04) s'il est installé par `cargo install` ; seul binaire du paquet, il est lancé par `cargo run -p engramme-cli -- …` ; dans tous les textes, le programme s'appelle `engramme`, quel que soit `argv[0]` (`engramme-dev` sous cargo, un chemin quelconque sous Python).
Contrat de `run` pour J04 (`engramme-py` appellera `engramme_cli::run(sys.argv)` dans l'interpréteur Python) : `args` commence par le nom du programme, ignoré, comme `std::env::args_os()` et `sys.argv` ; `run` ne panique sur aucune entrée, n'appelle jamais `std::process::exit` (seul `main.rs` le fait), n'écrit que dans les flux reçus, ignore les erreurs d'écriture (tube fermé par `| head`) et vide les deux flux avant de rendre le code ; `run_with` reçoit `ENGRAMME_DIR` et les flux en paramètres, car `std::env::set_var` est `unsafe` en édition 2024 et `unsafe` est interdit : les tests en processus injectent `ENGRAMME_DIR` par `run_with`, seuls ceux qui lancent le binaire le fixent (`Command::env`, `Command::env_remove`).
Décisions : arguments analysés à la main (une sous-commande, deux options, des chemins ; `clap` ajouterait un arbre de dépendances à chaque construction de wheel et imposerait ses propres messages et codes ; J01–J02 ont refusé toute dépendance évitable), en `OsString` pour accepter les chemins non UTF-8 ; le rapport va sur stdout — une ligne `Display` par diagnostic, chemins affichés tels que donnés (jamais canonisés), puis toujours une ligne de bilan — et stderr ne reçoit que les erreurs d'utilisation : l'agent de la règle 7 du §4.1 lit stdout comme une liste de `fichier:ligne`, `grep` aussi ; codes de sortie : 0 sans erreur (avertissements permis), 1 avec au moins une erreur, 2 quand rien n'a été vérifié (ligne de commande invalide, ou aucun chemin et `ENGRAMME_DIR` absent, vide ou qui n'est pas un dossier) ; un chemin explicite inexistant n'est pas une erreur d'utilisation mais le diagnostic `unreadable-file` de `check_path` (code 1), au format que l'agent sait corriger ; chaque chemin est vérifié séparément, dans l'ordre donné (ni tri global, ni doublons cherchés d'un chemin à l'autre) ; `ENGRAMME_DIR` n'est lu que si aucun chemin n'est donné.
Conventions de J01–J02 : messages en anglais, sur une ligne, sans majuscule initiale ni point final, exacts entre « » (guillemets exclus) ; toute valeur citée dans un message (argument, `ENGRAMME_DIR`) passe par `one_line` (`to_string_lossy()`, `\r` et `\n` remplacés par des espaces) ; aucune dépendance externe nouvelle ; dans `src/`, ni `unwrap()`, ni `expect()`, ni `panic!` ; `#![forbid(unsafe_code)]` et `#![deny(missing_docs)]` dans `lib.rs`, `///` en anglais sur tout élément public.
