    3. `## Notes` :
       - Le frontmatter est facultatif. Il existe seulement si la ligne 1 est `---`, et se ferme à la **première** ligne `---` suivante : un scalaire de bloc YAML ne peut donc pas contenir de ligne `---`. Jamais fermé → `invalid-frontmatter` en ligne 1. YAML qui n'est pas un mapping → `invalid-frontmatter`.
       - Table des clés : `title` (chaîne) ; `tags`, `sources` (listes de chaînes ; vide ou `null` = liste vide).
       - YAML 1.2 : `yes`, `no` et `on` restent des chaînes, mais un nombre n'en est pas une (`tags: [2024]` → erreur ; écrire `"2024"`). Une clé de mauvais type donne `invalid-frontmatter` sur la ligne de sa valeur, et la clé est ignorée ; pour une liste en bloc ou un scalaire `|` ou `>`, c'est la première ligne du contenu. Les clés inconnues sont conservées et ignorées.
       - Titre : `title` non vide ; sinon le premier titre de niveau 1 (`# `, jusqu'à 3 espaces avant, `#` finaux retirés) hors blocs de cartes et hors blocs de code ; sinon le nom du fichier sans `.md`.
       - Corps : CommonMark et GFM, LaTeX entre `$…$` et `$$…$$`.
    4. `## Card blocks` :
       - Syntaxe, à partir d'un fragment. La ligne d'ouverture est en colonne 0 : `:::`, puis le type, sans espace (`::: qa` → `invalid-block-header`), puis éventuellement des blancs et `{#<id>}`, et rien d'autre (`invalid-block-header`). La fermeture est `:::` seul ; les blancs finaux sont tolérés.
       - Types, en minuscules : `qa`, `cloze` ; `free` et `estimate` sont réservés (`reserved-block-type`, bloc ignoré) ; tout autre type → `unknown-block-type`.
       - Un bloc sans fermeture donne `unclosed-block` sur sa ligne d'ouverture, y compris quand un autre bloc s'ouvre avant (pas d'imbrication). Une ligne `:::` isolée hors bloc est ignorée sans diagnostic.
       - Bloc de code délimité (``` ou ~~~, au moins 3 caractères, jusqu'à 3 espaces d'indentation, fermé par au moins autant du même caractère) : les lignes `:::` et `---` qu'il contient ne comptent pas. Jamais fermé hors d'un bloc de carte → `unclosed-code-fence` (avertissement) et les blocs de cartes suivants sont ignorés ; dans un bloc de carte, c'est le bloc qui est signalé non fermé. Un bloc en erreur ne produit aucune carte.
       - Identifiants : `c-` puis 6 à 8 caractères `[0-9a-z]` (`malformed-id`), tirés au hasard et attribués par l'app seule (sous-projet 2), jamais par un humain ni un agent. Une carte sans identifiant est valide. Un doublon parmi les notes de la base donne `duplicate-id` sur chaque occurrence après la première, qu'il cite. Une note vérifiée seule ne voit que ses propres identifiants. L'historique suit l'identifiant : modifier le texte le conserve, supprimer le bloc retire la carte de la révision.
    5. `### qa` : le recto, la première ligne `---` hors bloc de code (exactement `---` en colonne 0, blancs finaux tolérés), puis le verso. Les `---` suivants appartiennent au verso ; le recto ne peut pas en contenir (utiliser `***` pour un trait). Les lignes vides aux bords de chaque face sont retirées. Diagnostics : `missing-separator`, `empty-face`.
    6. `### cloze` :
       - Trous `{{cN::text}}` et `{{cN::text::hint}}`, avec N ≥ 1 sans zéro initial. Les trous de même N sont masqués ensemble ; chaque N distinct donne une sous-carte `<id>.<N>`.
       - L'indice commence au **premier** `::`, comme dans Anki : `{{c1::std::mem::take}}` masque `std` avec l'indice `mem::take`. Écrire plutôt `std::mem::{{c1::take}}`.
       - Le trou finit au premier `}}` hors accolades ouvertes : les accolades LaTeX équilibrées passent (`{{c1::\frac{a}{b}}}`). Les trous sont reconnus partout dans le corps, LaTeX et code compris ; un `{{c` qui n'est pas suivi de chiffres puis de `::` reste du texte.
       - Diagnostics : `no-cloze-deletion` (aucun trou) ; `invalid-cloze-deletion` (texte vide, `c0`, `c01`, trou jamais fermé) ; `non-consecutive-cloze-numbers` (avertissement, par exemple c1 et c3 sans c2).
    7. `## Inbox proposals` :
       - Un fichier par proposition, directement dans `inbox/`. Nom `<YYYY-MM-DD>T<HHMM>-<agent>-<topic>.md` : une date et une heure réelles, puis au moins deux mots `[a-z0-9]+` séparés par `-`. Si le nom existe déjà, suffixe `-2`, `-3`, etc. Un nom non conforme donne `unexpected-file-name` (avertissement).
       - Frontmatter obligatoire ; sans frontmatter → `missing-required-key` en ligne 1. Table des 5 clés (`proposed_by`, `date`, `context`, `target`, `why`) : chaînes non vides ; une clé manquante donne `missing-required-key` en ligne 1, une clé vide sur sa propre ligne.
       - `date` : `YYYY-MM-DDTHH:MM`, puis éventuellement `:SS` et une fraction, puis éventuellement `Z` ou `±HH:MM`, pour une date réelle. Refusés (`invalid-frontmatter`) : `2026-10-20 14:32`, `2026-10-20T14:32:00+0200`, `2026-10-20` seul.
       - `target` : chemin relatif avec des `/`, sous `notes/`, finissant par `.md`, sans composant vide, `.`, `..` ou caché (`invalid-target`). La note n'a pas besoin d'exister.
       - `tags` et `sources` sont facultatifs ; ils sont fusionnés dans la note à l'acceptation. Les clés inconnues sont conservées.
       - Corps : de la prose facultative, puis 1 à 3 blocs `qa` ou `cloze` sans identifiant (`no-card` ; `too-many-cards` sur le 4ᵉ bloc ; `id-in-proposal`). Les blocs réservés ne comptent pas.
       - Tri carte par carte : accepter, modifier puis accepter, ou rejeter avec un motif. Avant l'app, à la main : copier ce qu'on garde dans la note, puis supprimer le fichier.
    8. `## Event log` : le §3.5 tel quel. Un fichier par mois UTC et par appareil ; `<device>` suit `[a-z0-9-]+` et se règle hors de la base ; ajout seul ; champs communs `ts` et `ev` ; table `review`, `suspend`/`unsuspend`, `triage`.
